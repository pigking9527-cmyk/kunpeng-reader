# 同步容量与高负载验收

## 当前阶段目标

本文早期的 PostgreSQL 数字来自已移除的 Python 服务，仅保留为历史回环保护性
参考；它**不是** Rust Axum v5 的部署、迁移或容量证据。容量演练只能使用
`server/reader-sync-api-rs/scripts/run-capacity-test.sh` 及其受保护目标门禁；完整流程见
[`sync-api-v5-postgres-rehearsal.md`](sync-api-v5-postgres-rehearsal.md)。
它使用 k6 保活连接和至少 2048 个互不共享会话的可销毁测试账户；同一账户写入的 503 保护
不应被当成全服务容量结论。

## Pull 工作负载档位

默认 `catchup` 是正常容量档位：固定 20 分钟曲线的每个阶段使用对应数量的
独立 k6 VU，不存在全局批次栅栏。每个 VU 持有自己的 cursor、checkpoint 状态和
与同阶段其他 VU 不重叠的账户分片；它一收到响应就可以继续处理自己的下一账户，
不会因另一个慢请求阻塞整个阶段。正式曲线使用一个固定 500 VU 的
executor，但每阶段只激活前 N 个 VU。报告以
`concurrencyUnit: active-independent-k6-vus`、`executorConfiguredVus`、`activeVus` 和
`httpInFlightUpperBound` 区分执行器大小与当前阶段的实际并发。

每个账户从 `cursor=0` 开始补追，只在成功响应后保存自己的 `nextCursor`；
无变更 pull 改用 checkpoint，checkpoint 返回 false 后再做正常 pull。容量 push 使用每账户
稳定实体 ID，但每次单调更新 `updatedAt`、`syncVersion` 和 payload，不得在首次写入后
退化成 no-op。每账户请求间隔至少 1.2 s；报告同时校验每阶段恰好声明
0..N-1 的 VU 分片、覆盖全部 2048+ 账户，并记录请求/字节配额上界；任一门禁失败
都不得形成容量结论。

`--independent-smoke N` 是固定 60 秒的非容量诊断，它使用与正式曲线相同的独立 VU
和分片模型，但不具备时长与恢复阶段。报告必须标记
`workloadClass: non-capacity-diagnostic`、`executionModel: independent-vus` 和
`capacityConclusionEligible: false`。它必须覆盖全部 2048+ 账户，但不得取代固定
20 分钟容量曲线。`--short` 同样只是 330 秒排练，报告标记
`workloadClass: capacity-rehearsal` 且不具备容量结论资格。
旧 `http.batch` 全局栅栏只保留为单阶段 `--smoke N` 突发诊断，报告标记
`workloadClass: non-capacity-burst`，不得再用来声明服务稳定吞吐。

checkpoint 响应体在 k6 全局丢弃响应体时仍必须显式保留为文本；否则
`caughtUp` 无法解析，会把本应走轻量 checkpoint 的账户错误降级成 full pull，
并系统性低估稳态容量。

每个阶段还记录 `completedRequests`/`completedRequestsPerSecond` 与
`successfulRequests`/`successfulRequestsPerSecond`。前一组只计入实际收到 HTTP 响应的请求
（不含 k6 status 0）；后一组只计入 2xx，才是有用的同步处理吞吐。两组的每秒值均以各阶段
计数除以该阶段计划秒数。它们必须和 P50/P95/P99、状态码及硬件负载一起解读，不能把发起并发
数误作每秒处理能力。

## 前台与维护任务隔离

`push` 的事务只保留必须原子完成的 LWW 写入、配额账本和幂等收据；过期收据裁剪及
阅读背景的孤儿标记/回收由单个有界后台任务处理。收据每五分钟最多裁剪 2,000 行，
资产每小时最多检查 100 个账户；拿不到同账户事务锁时直接跳过并在后续周期重试，
不会在写入锁后排队。后台指标仅以固定任务名和聚合数量记录，不能包含账户、资产、
请求或内容。容量报告应将这些后台批次视为独立、低优先级负载，而不是同步请求耗时。

`cursor-zero-replay` 是必须显式选择的对抗回放档位：它故意让每次 pull 都使用 `cursor=0`，用于
观察最坏的历史回放与写入竞争。它不是正常客户端行为，报告会标记
`workloadClass: adversarial` 和 `capacityConclusionEligible: false`；不得将其 P95/P99、状态码或
硬件负载作为默认容量结论。运行器一次只执行一个档位，绝不自动混合两种档位；两者必须分开
运行、分开报告和比较。

### 写突发与 503 定向优化后回归

旧独立 VU 模型使所有 VU 同时起跑，并用线性的 `accountIndex % 20` 选操作。40 VU 与
20 操作槽整除时，固定一组 VU 会长期同相 push，人为放大写突发。现行诊断模型使用固定
seed `0x6d2b79f5` 哈希化账户起点和操作相位，保持每 20 次访问精确 14 读、5 push、1 inventory；
每阶段首请求做 0–999 ms 确定性错峰。独立模式使用 3 秒 `gracefulStop`，并要求发起与
记录的请求数精确相等、`stageCutoff == 0`；账目不全的报告不再被标为完整。

服务在本轮定向优化初步保留 18 个写执行位，只将有界写等待位从 16 增至 48，以吸收短时 push 错峰；
数据库连接获取超时从 200 ms 增至 300 ms。请求队列上限仍为 200 ms，没有增加同时执行的
写事务或数据库连接数。服务指标新增低基数的 `apiErrors`、`busySources`、
`databaseFailures` 和 `queueRejectionReasons`，可区分队列满、准入补租竞争、账户写锁与
数据库 acquire/query 失败，不改变 HTTP 或 v5 wire 语义。

新参数已在隔离测试服务上诊断确认生效，未触及正常服务。使用新负载模型的回归如下：

- 51 VU 三轮共 264,880 个请求，264,871 个 2xx、无无响应、无写队列拒绝。服务重启后
  首轮有 9 个 `DATABASE_UNAVAILABLE`，全部为 `auth/acquire`；后两轮 503 为零。三轮成功
  RPS 为 1,570.57/1,607.65/1,236.30，第三轮主机 CPU 94.59%、PostgreSQL 132.56%，显示
  51 VU 仍可在冷启动和 CPU 饱和时失去稳定性。
- 40 VU 三轮共 228,442 个请求，全部为 2xx，503、无响应、截止、Busy、数据库失败和
  队列拒绝均为零。前一轮受上轮高负载余波影响，成功 RPS/P99 为 1,074.23/106.25 ms；
  后两轮为 1,354.12/55.14 ms 和 1,379.02/51.01 ms。
- 30 VU 十轮共 616,729 个请求，616,728 个 2xx，503、Busy、数据库失败、队列拒绝和
  截止均为零；唯一失败是客户端 `pull` request timeout，不是服务端 503。平均成功吞吐
  1,027.88 RPS，范围 974.23–1,065.15；平均 P99 45.68 ms，范围 41.37–67.13 ms。
  主机/PostgreSQL CPU 平均分别为 63.47%/71.26%，每轮连接池至少保留 27 条空闲连接。

因此，当目标是尽量避免服务端 503 时，30 VU 仍是当前重复证据最强的短测运行点；
40 VU 在新模型下三轮无错，可作为更高吞吐候选，但还不是长时间 SLO 结论。51 VU 不应被宣称为
零 503 稳定并发。上述全是 60 秒非容量诊断；完整 20 分钟新基线仍需单独重跑。

### 40 总执行预算与客户端超时余量

30–40 VU 逐档一分钟诊断中，40 VU 为 81,639/81,639 个 2xx、1,360.65 成功 RPS、
P99 51.56 ms、503 和无响应均为零。31、36、38 VU 各有一次 k6 两秒 `pull` request timeout，
对应阶段的服务端 error、Busy、database failure 和 queue rejection 指标均为零；39 VU 首轮更出现
4,135 次无响应且主机 CPU 反而降至 54.36%，补跑后 80,856/80,856 全部成功。这组特征属于
压测链路超时，不是服务处理能力拒绝。

服务默认执行预算随后收敛为普通读 12、checkpoint 18、写 10，三个互相隔离的 lane 合计最多
40 个执行请求。连接池仍为 48，保留连接交接余量；各 lane 仍使用独立有界等待位和 200 ms 排队
截止，不会为了减少客户端超时而无界排队。在隔离服务确认新预算生效后，40 VU 连续三轮共
250,896 个请求全部为 2xx；503、无响应、Busy、数据库失败、队列拒绝和 cutoff 均为零。
三轮成功 RPS 为 1,358.87/1,398.58/1,424.15，平均 1,393.87；平均 P99 51.63 ms，主机与
PostgreSQL CPU 平均分别为 77.62%/90.68%。

桌面同步客户端的单次请求截止从 15 秒调为 20 秒，严格长于服务端默认 15 秒 handler 截止；
这样服务有时间返回结构化 504，客户端可按现有策略做最多 3 次、750/1,500 ms 基础延迟加抖动的
有界重试。超时、传输错误和 5xx 可重试，429 不在同一次同步中立即重试；push 的 mutation ID 保证
重试幂等。容量 k6 仍保留更严格的两秒超时，以暴露链路或服务尖峰，不通过放宽压测截止美化数字。

### Windows SSH 隧道 50 VU 连接交接余量复测

2026-08-21 从 Windows 经 SSH 回环隧道执行固定 60 秒 `--independent-smoke 50`。该链路的
业务请求 P50 约为 53 ms，按闭环并发关系只能形成约 900–930 RPS；它不能与近服务压测机
约 28 ms P50、超过 1,500 RPS 的结果直接比较，也不能据此判定服务吞吐退化。

调优前的隔离服务使用 48 条连接、300 ms 获取截止：55,787 个请求中 55,770 个成功，
出现 15 个 `auth/acquire DATABASE_UNAVAILABLE` 503，以及 2 个跨轮 mutation ID 冲突 409，
成功吞吐 929.50 RPS。隔离服务随后把连接池提高至 56、获取截止提高至 600 ms；普通读、
checkpoint、写执行 lane 仍为 12/18/10，因此不会增加同时执行的 SQL 数。正式服务未改动。

容量探针的 mutation ID 同时加入运行批次、阶段与序号，避免不同测试轮次复用同一幂等键。
修正后复测为 54,955/54,955 个 2xx，503、409、429、500、无响应、队列拒绝、数据库失败和
cutoff 均为零；成功吞吐 915.92 RPS，P50/P95/P99 分别为 53.37/64.48/83.42 ms，覆盖
2,048 个独立测试账户。主机 CPU 平均/峰值 63.71%/82.70%，API 为 37.25%/44.67%，
PostgreSQL 为 61.30%/83.38%；连接池最多使用 47 条、最少保留 37 条空闲连接，服务器最低
可用内存 2.80 GiB。Windows 压测进程 CPU 平均 26.87%，RSS 峰值 83.90 MiB，最低可用
内存 6,671.49 MiB。

这次结果只证明 Windows 隧道下 50 VU 的一分钟冷会话诊断稳定性，不替代固定 20 分钟容量
基线，也不能外推为生产容量上限。

### Windows 直连 HTTPS 与原生 SSH 传输对照

2026-08-21 使用同一台 Windows 压测机、同一个无数据库访问的 `/health` 处理器和同样的
50 个持续 VU，各执行 60 秒闭环传输对照。公网 HTTPS 轮次为 115,128/115,128 成功，
1,918.13 RPS，P50/P95/P99 为 24.98/34.38/41.55 ms，全部连接复用后的响应使用 HTTP/2；
单条原生 Windows OpenSSH 回环隧道轮次为 87,171/87,171 成功，1,451.55 RPS，
P50/P95/P99 为 34.38/37.48/41.97 ms，隧道内应用连接使用 HTTP/1.1。两轮均无非 200、
无响应或截止。直连 HTTPS 的吞吐高 32.1%，P50 低 9.40 ms；差异来自少一层 SSH 转发以及
HTTP/2 复用，不是 macOS/Windows 计算性能差异。TLS 和 TCP 连接量化指标的 P95 为零，说明
绝大多数请求复用了既有连接，不能据此理解为没有首次握手成本。

SSH 隧道使用持久连接、关闭压缩、吞吐型 IP QoS 和 TCP keepalive。随后只对回环隔离服务及
可销毁测试库补跑真实同步混合：50 VU、60 秒共 55,063/55,063 个 2xx，成功吞吐
917.72 RPS，P50/P95/P99 为 53.43/60.50/82.56 ms；503、409、429、500、无响应均为零，
覆盖 2,048 个独立测试账户。公网 HTTPS 后端不是测试库，因此没有用测试会话执行直连业务
负载；隔离测试端口也继续遵守不得接入反代的边界。

这组数据证明 Windows 客户端应优先使用直连 HTTPS，SSH 只适合作为运维或隔离测试通道。
健康端点对照只是传输基准，不能代替业务容量或固定 20 分钟容量测试。

## 验收阈值

- 健康检查 32 并发：无进程崩溃、无数据库损坏，成功与明确 429/503 之和为 100%；
- 同步 pull 20 并发：P95 小于 500 ms；
- 小批 push 8 并发：P95 小于 1 s，最终实体与库存摘要一致；
- SQLite 兼容测试退出后 `PRAGMA quick_check` 必须为 `ok`；生产 PostgreSQL 必须开启数据页校验并通过定时只读查询；
- 压测不得使用生产账户、用户阅读内容或无限请求数。

2026-08-12 的旧服务回环保护性探针使用 100 个健康请求、32 并发：59 个成功、41 个按设计返回 429，无 5xx、断连或进程重启；整体 P50 8.95 ms、P95 30.12 ms、P99 1018.68 ms。限流后的监控与 SQLite `quick_check` 继续通过。该结果只证明旧服务的突发退化边界，不代表 Rust v5 或认证 pull/push 的容量上限。

## 迁移信号

以下任一项持续出现即进入 PostgreSQL 迁移：SQLite 锁错误、写入 P95 超 500 ms、429/503 超过正常请求的 1%、需要多进程或多主机、数据库达到数 GiB。短时压测中的保护性 429/503 本身不是数据错误。

## 持续监控

监控、数据库完整性校验、逻辑/物理备份和 WAL 归档必须由实际部署的 Rust/Axum v5
环境重新验证。Python 服务的旧监控脚本已删除，历史数字不能作为上述能力的证据。

2026-08-12 的旧服务迁移记录仅表明当时的历史环境曾完成一次快照核对；它不构成
Rust v5 的验收。v5 的容量、备份恢复与反代演练必须在独立受保护测试数据库重新生成。
