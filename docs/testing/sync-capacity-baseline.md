# 同步容量与高负载验收

## 当前阶段目标

本文早期的 PostgreSQL 数字来自已部署的旧 Python 服务，仅可作为旧服务的回环保护性
基线；它**不是** Rust Axum v4 的部署、迁移或容量证据。Rust v4 仍须先在独立空测试库
执行受保护的 PostgreSQL E2E、备份/恢复与反代演练，之后才能安排可回滚切换。

开发机或旧服务的服务器回环地址仍可使用同一有界压测工具：

```bash
python3 server/reader-sync-api/load_test.py --base http://127.0.0.1:8787 --path /health --requests 1000 --concurrency 32
```

认证端点通过环境变量传入专用测试 Token；脚本不会打印 Token。远端目标默认被拒绝，只有明确设置 `ALLOW_REMOTE_LOAD_TEST=1` 才允许。

## 验收阈值

- 健康检查 32 并发：无进程崩溃、无数据库损坏，成功与明确 429/503 之和为 100%；
- 同步 pull 20 并发：P95 小于 500 ms；
- 小批 push 8 并发：P95 小于 1 s，最终实体与库存摘要一致；
- SQLite 兼容测试退出后 `PRAGMA quick_check` 必须为 `ok`；生产 PostgreSQL 必须开启数据页校验并通过定时只读查询；
- 压测不得使用生产账户、用户阅读内容或无限请求数。

2026-08-12 的旧服务回环保护性探针使用 100 个健康请求、32 并发：59 个成功、41 个按设计返回 429，无 5xx、断连或进程重启；整体 P50 8.95 ms、P95 30.12 ms、P99 1018.68 ms。限流后的监控与 SQLite `quick_check` 继续通过。该结果只证明旧服务的突发退化边界，不代表 Rust v4 或认证 pull/push 的容量上限。

## 迁移信号

以下任一项持续出现即进入 PostgreSQL 迁移：SQLite 锁错误、写入 P95 超 500 ms、429/503 超过正常请求的 1%、需要多进程或多主机、数据库达到数 GiB。短时压测中的保护性 429/503 本身不是数据错误。

## 持续监控

部署后，生产机只从回环地址读取健康与 Prometheus 指标，并使用私密环境中的 `SYNC_DATABASE_URL` 验证 PostgreSQL 版本、数据页校验、非恢复状态与 schema 可读性：

```bash
SYNC_DATABASE_URL=... python3 server/reader-sync-api/health_monitor.py
```

监控输出不包含账号、令牌、邮箱、实体内容或真实 IP。默认在活动请求超过 28，或至少 20 个样本的累计平均延迟超过 500 ms 时失败；部署环境可以收紧阈值并由 systemd timer/外部告警系统接收非零退出码。

2026-08-12 的旧服务迁移记录：停写快照与 PostgreSQL 18.4 的 18 张表、11,665 行、4,664 实体和库存摘要一致。它不构成 Rust v4 的验收；v4 的演练和备份恢复记录必须在独立测试数据库单独生成。每日逻辑转储、物理基备份、WAL 归档和异地对象存储也都必须由 v4 的实际部署环境重新验证。
