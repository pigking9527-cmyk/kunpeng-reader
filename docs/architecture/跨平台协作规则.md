# 跨平台协作规则

## 目标

鲲鹏阅读器覆盖 Windows、macOS、Linux、Android、iPhone 与 iPad。统一的目标不是“一次写 UI、到处运行”，而是：

> 一套产品语义、同步协议、测试样本和发布规则；桌面、Android、Apple 各自采用适合平台的界面实现。

桌面端继续采用 Tauri + Rust + Web UI；Android 建议 Kotlin + Jetpack Compose；iOS/iPadOS 建议 SwiftUI。同一功能在不同屏幕上可以用不同导航与布局，但保存的数据和用户可见语义必须一致。

## 共享层与平台层

| 层 | 是否统一 | 说明 |
| --- | --- | --- |
| 产品术语与行为 | 必须统一 | 阅读进度、书签、高亮、批注、标签、书单、评分、统计、删除和冲突含义。 |
| 同步 API 与实体协议 | 必须统一 | 以 `contracts/` 为唯一事实来源。 |
| 兼容性 fixtures | 必须统一 | 所有端对同一输入输出做验证。 |
| 本地数据库实现 | 可以不同 | 可使用 SQLite、GRDB、Room 等；不得把本地表结构当 API。 |
| UI、导航、手势、排版 | 可以不同 | 桌面菜单、iPhone sheet、iPad sidebar、Android bottom sheet 可各自原生。 |
| 阅读渲染 | 逐步共享 | EPUB 解析、文本定位等纯逻辑可后续抽到 Rust core；不要为了共享而重写稳定桌面阅读页。 |

## 单仓库目标结构

```text
apps/
  desktop/                 # 将来可映射现有桌面根目录，不在功能开发中贸然移动
  android/                 # Kotlin + Compose
  ios/                     # 一个 SwiftUI 工程，同时支持 iPhone/iPad
crates/
  reader-domain/           # 将来抽取的纯模型与规则
  reader-core/             # 将来抽取的 EPUB/文本定位能力
contracts/
  sync/ fixtures/ compatibility/
server/
  reader-sync-api-rs/
docs/
  architecture/ adr/ coordination/
```

当前尚未完成移动端迁入，所以先把 `contracts/`、ADR 与协作规则放在桌面仓库作为规范中枢。等 Android/iOS 工程稳定后再迁入，或以 Git subtree/明确的版本依赖接入；不要在两个仓库各自复制一份协议文件后长期手改。

## 版本策略

- **产品版本**：例如 `1.10.0`，面向用户的功能集合。
- **平台构建版本**：例如 desktop `1.10.0`、android `1.10.1`；允许单端热修。
- **同步协议版本**：`syncProtocolVersion`，只在实体/API 语义发生不兼容变化时升级。

服务端应至少兼容上一协议版本。客户端必须声明自身协议版本与能力，不能假定服务器永远和本端同时升级。

## 共享变更流程

1. 先在 ADR 说明问题、决定与兼容范围；
2. 更新 schema 与 fixtures；
3. 服务端先做到向后兼容；
4. 桌面、Android、Apple 分别实现；
5. CI 在每个端运行契约兼容测试；
6. 完成后更新 `CURRENT.md`。

不影响数据含义的 UI 改动直接在本端完成，无需走此流程。

## 分支与发布

- 只保留 `main` 长期主干，功能使用短分支：`feature/android-reader`、`feature/ios-sync`、`fix/desktop-pagination`。
- 不建立长期的 `android-main` 或 `ios-main`，避免协议和行为分叉。
- 同一 GitHub Release 可附 Windows/macOS/Linux/Android 产物与对应 SHA-256；iOS 发布 TestFlight/App Store 时，Release 写明链接和版本，不上传不可安装的签名归档。
