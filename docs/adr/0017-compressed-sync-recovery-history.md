# ADR-0017：云端同步数据采用压缩实体历史与分层快照

## 状态

已废弃（2026-08-14）。产品不再提供云端历史版本恢复，客户端入口与命令、服务端路由和历史写入均已移除；数据库迁移 `0018_remove_recovery_history_v5.sql` 物理删除旧历史表。以下内容仅保留为历史决定记录，不再描述当前实现。

## 背景

同步服务过去只保存每个实体的当前版本。旧客户端错误写回、误删除或程序缺陷一旦通过 LWW 成为当前状态，服务端没有独立证据恢复覆盖前的数据；只备份整库又会重复保存大量未变化实体，随用户量增长浪费存储。

## 决定

服务端增加两层恢复能力：

1. **实体级增量历史**：只有服务端实际接受的新实体版本才新增历史行；重复投递、冲突失败和校验拒绝不产生历史。每行保存该实体的完整 JSON，而不是字段差异，并使用 zlib level 6 压缩、记录原始长度和 SHA-256。恢复不依赖连续重放差异链。
2. **数据库级压缩快照**：使用 SQLite Online Backup API 创建一致性副本，`PRAGMA quick_check` 通过后以 gzip level 6 压缩、生成 SHA-256，并按最近 7 个日备份、4 个周备份、12 个月备份轮换。生产环境应把输出目录同步到 OSS/COS 等独立故障域；真实桶、密钥和远端路径只在服务器私密配置中保存。

历史滚动窗口为 90 天。清理窗口外版本时，每个实体仍保留窗口前最新的一条锚点，使窗口内任意时间点都能重建完整账号状态。首次部署为已有实体写入一次基线；不能声称可恢复到基线启用以前。

`GET /sync/recovery/status` 只返回可恢复起点、最近版本时间、版本数和压缩前后字节数，不返回历史内容。`POST /sync/recovery/restore` 必须同时具备有效登录令牌、登录密码、当前 `data_generation`、布尔值 `confirm: true` 和目标服务端毫秒时间。

恢复按目标时间为每个实体选择最后一个完整版本。目标时间之后才出现的实体写成新墓碑，不能直接消失；恢复实体统一使用新的服务端时钟和 `server-recovery` 设备 ID。成功后递增 `data_generation` 并撤销该账号所有令牌，阻止旧设备立即重新上传恢复后的错误状态。

`secret_bundle_v1` 不进入时间点历史，也不参与恢复，避免重新启用已经撤销的加密密钥世代。用户主动执行“清除此设备及云端”或永久删除账号时，同时物理删除该账号的实体历史和恢复元数据；恢复机制不能绕过明确的数据删除请求。

## 兼容性影响

同步实体协议和 `syncProtocolVersion` 不变。旧客户端无需理解历史表或恢复 API，正常 push/pull 行为不变。恢复成功后世代递增，旧客户端必须遵循 ADR-0006 的世代规则重新登录和拉取。

服务端 API 版本提升为 0.9；恢复 API 是加法扩展。对象存储快照不进入同步协议，不下发客户端。

## 替代方案

字段级 delta 更节省少量空间，但恢复依赖完整差异链，任一记录损坏都会影响后续版本；同步实体 JSON 通常很小，不值得承担该风险。每天复制每个账号的完整状态实现简单，但会重复保存几乎全部未变内容。仅保留同盘 SQLite 历史无法抵御磁盘或主机损坏，因此同时保留独立压缩快照。

## 迁移与回滚

部署时创建 `entity_history`、`recovery_accounts` 和索引，并为现有可恢复实体写入压缩基线。迁移在一个 SQLite 事务内完成，重复启动不会重复播种。回滚旧服务端可以忽略新增表；不得在未确认快照可用前删除历史表。

生产启用前先执行一次压缩快照并在独立目录解压、`quick_check`、读取实体抽样验证。服务器应用部署和对象存储上传参数仍按私密运维流程完成。

## 验证

- 只对服务端实际接受的变化产生历史，重复 push 不增加版本；
- 压缩历史可校验 SHA-256、长度并还原完整 JSON；
- 90 天清理保留每个实体的一个窗口前锚点；
- 时间点恢复覆盖旧值，目标后新实体变为墓碑；
- 恢复递增 `data_generation` 并撤销令牌；
- 密钥包不进入历史；主动云端清除和账号删除同时清除历史；
- SQLite 快照通过 `quick_check`、gzip 解压与 SHA-256 校验，并正确轮换日/周/月恢复点。
